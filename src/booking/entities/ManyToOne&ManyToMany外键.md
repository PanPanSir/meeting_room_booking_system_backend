@ManyToOne(() => User)
  @JoinColumn({
    name: 'user_booking',
  })
  user: User;
@ManyToMany(() => User)
  @JoinTable({
    name: 'user_booking',
  })
  user: User;

## 一. 以下是两种配置的建表效果差异分析（结合参考内容）：

1. **`@ManyToOne + @JoinColumn`**
   - **表结构**：在**当前实体对应的表**（例如 `Booking` 表）中新增 `user_booking` 字段作为外键，直接指向 `User` 表的主键（如 `id`）。
   - **关系表达**：表示“多对一”关系（例如多个预订记录属于一个用户），查询时通过单表外键直接关联，无需中间表。
   - **性能影响**：直接通过外键字段查询，效率较高（符合参考内容中提到的避免中间表对性能的影响）。

2. **`@ManyToMany + @JoinTable`**
   - **表结构**：生成**独立中间表** `user_booking`，包含两个外键字段（如 `booking_id` 和 `user_id`），分别指向关联的两个实体表（如 `Booking` 和 `User`）。
   - **关系表达**：表示“多对多”关系（例如一个用户可以有多个预订角色，一个预订角色可分配给多个用户），必须通过中间表维护关联。
   - **性能影响**：查询时需联合中间表和关联表，数据量大时可能存在性能瓶颈（参考内容中提到的中间表性能问题）。

| **对比点**         | `@ManyToOne + @JoinColumn`                          | `@ManyToMany + @JoinTable`                          |
|--------------------|----------------------------------------------------|----------------------------------------------------|
| **外键存储位置**    | 当前实体表（如 `Booking.user_booking`）            | 独立中间表（如 `user_booking` 表的 `user_id`）     |
| **关系类型**        | 单向多对一（从当前实体指向目标实体）               | 双向多对多（需中间表维护双向关联）                 |
| **冗余数据风险**    | 无（外键直接引用目标表）                           | 无（中间表仅存储关联ID，避免数据冗余）             |
| **适用场景**        | 简单层级关系（如订单-用户、评论-文章）             | 复杂交叉关系（如用户-角色、学生-课程）             |

**关键结论**：
- 若使用 `@ManyToOne` 时省略 `@JoinColumn`，根据参考内容提示，可能自动生成中间表（但此例中已显式声明，故不会发生）。
- `@JoinTable` 的 `name` 参数定义的是中间表名，而 `@JoinColumn` 的 `name` 参数定义的是当前表的外键字段名——尽管两者都命名为 `user_booking`，但实际作用完全不同。

## 二. 查询效率

严格来说：使用外键（@ManyToOne）的查询效率通常低于仅用索引

原因：外键约束会触发数据库的完整性验证（如检查关联数据是否存在），增加额外开销。参考内容明确指出“加外键会降低性能”（2017年知乎回答）。
例外场景：若未手动为外键字段创建索引，此时外键可能自带隐式索引，反而比无索引的关联查询更快。但这属于索引的优化效果，而非外键本身的优势。
实际工程中的取舍

高并发场景：多数互联网应用会放弃外键，仅通过代码保证数据完整性（参考2015年知乎回答）。此时：
✅ 写入性能更高（无外键约束的锁竞争）
✅ 查询性能依赖手动添加索引，与外键方案持平甚至更优
强一致性场景：银行/政务系统可能保留外键，牺牲部分性能换取数据强一致性。
